## Exit crashes (`0x4CF360`, `0x4AC7D6`, `0x13943F`, `0x1BD6A0`)

The Event Log is dominated by faults within a second of the process ending; the owner never sees them. Counted over 120 days (2026-10-23): 37 `witcher.exe` faults, 27 of them these four, and **none of the four before 2026-10-20 11:21**.

Cause found (2026-10-23), **not solved**: they are ours. QoL 2's pause-menu "Exit game" called `ExitProgram(0)` with the system panel still registered, while `gui_mainmenu.luc` `_ExitProgram` deactivates, deletes and clears its panel first. Evidence: four WER full dumps all caught a shutdown crash — `0x4CF360` = `FUN_004cf340` with `this = NULL` (first access `[this+0x164]`), and `0x53943F` = `FUN_005393c0`, the script/console command dispatcher, with a garbage `this` — and 18 of 18 `pause menu: Exit game` lines are followed 1-2 s later by one of the fault events.

Tearing the panel down before `ExitProgram` (mirroring the main menu) **did not fix it**: retested in game 2026-10-23 21:43, `0x13943F` one second after the click. The remaining difference is quitting with an area loaded: the fault is inside `FUN_005752a0`, the `CAurObject` destructor, dispatching the `Dying` script event through `FUN_005393c0` after the script system is gone. Main-menu exits, with no area loaded, have never produced one of these faults. So the engine's shutdown assumes no in-game state — the reason the game only offers "Exit to main menu" while playing. See [qol2-pause-exit-button.md](fixes/qol2-pause-exit-button.md).

Still open: the in-play crashes `0xA6525C` and `0x7223BB` predate WER LocalDumps, so no dump exists for them. `0x9FFFE0` and `0xA656CC` now have full dumps (next section).

## Karma constraint pool (`0x9FFFE0`, `0xA656CC`)

The game's physics is MathEngine Karma (`Mdt`/`Mcd`/`Mst` strings, `dumpkarmapool`). Both in-play crashes with a full dump are inside Karma, reached from the game's physics update `FUN_008377e0` (fixed-step loop calling `FUN_009f4d00`, the universe step: "Collision" then "Dynamics") or its teardown `FUN_00837490`.

Karma's fixed-size pools (`MePoolx`) are called through a function table: `0x00C31308` create `FUN_009fd810`, `0x00C3130C` destroy, `0x00C31310` reset `FUN_009fd7e0`, `0x00C31314` get `FUN_009fd8e0`, `0x00C31318` put `FUN_009fd900`, `0x00C3131C` used count, `0x00C31320` free count. Pool layout: `+4` block base, `+8` pointer stack, `+0xC` used count, `+0x10` block size, `+0x14` capacity. Get returns `stack[used++]`, put does `stack[--used] = p`; nothing checks that `p` is allocated, so a double put leaves `p` twice on the free part of the stack.

The world (`0x6C7D5CC0` in the dump) keeps every constraint (joints and contact groups) in a `MeDict` at `world+0x34` (node at constraint `+0x48`, comparator at dict `+0x20`, count at dict `+0x18`), and joints, contact groups and contacts all come from one pool at `world+0x12C` (block size `0x210`, capacity 20000). Constraint create: `FUN_009f85a0` (get) → `FUN_009f77c0` (zero the block, insert into the dict). Constraint destroy: `FUN_009f7bc0` → `FUN_009f7be0` (disable, for a contact group destroy its contacts via `FUN_009f8670`, remove from the dict with `FUN_00a001e0`, which zeroes the node links, type `+0xB0` = -1) → put. Contact destroy: `FUN_009f7540` (unlink from the group's list `+0x168`/`+0x16C`, next/prev at `+0x5C`/`+0x60`) → put. A new contact group per colliding model pair is made in `FUN_00a0ec50` and stored in the pair at `+0x18`.

The 02:28 dump: `FUN_00a0ec50` asked for a new contact group and got `0x6C9FF290`, which was the **root of the dict** (a live joint, type 9). `FUN_009f77c0` zeroed it and the insert walked into its zeroed child pointer. The pool's pointer stack, read out of the dump, has **14 of the 19 reachable dict nodes on its free part** (used 26 of 20000; among the next to be handed out are a live joint and a live contact group), all with intact type fields and dict links, so they never went through constraint destroy. No pointer occurs twice on the free part any more, and the dict count (23) exceeds the reachable nodes (20). This is what double puts leave behind once each duplicate has been handed out again: the second copy of `p` stays on the free list while `p` is live. Which caller puts twice is not in the dump. A candidate is a contact group destroyed twice (once with its body, `FUN_009f3cd0` destroys every constraint on the body, and once through the model pair that still holds it at `+0x18`), but this is not shown.

Candidate fix and diagnostic: [fix 14](fixes/fix14-karma-pool.md) (installed 2026-10-25, not verified in game). It wraps the pool table with a free bit per block, skips and logs second frees (also at the entry of constraint and contact destroy), and holds freed blocks in a short queue so a later second free is still caught. The `0xA656CC` teardown crash may be a consequence of the same corruption; fix 14 does not touch that path directly.

## Autosave on area transitions

Each autosave spends ~0.3-0.5 s in zlib: byte-at-a-time CRC32 `FUN_00800010` (table at `0xBC6610`), `inflate_fast`-like `FUN_00803860`, deflate window code `FUN_007feaf0`. The CRC part is fixed (fix 5). Deflate is zlib 1.1.4; a lower compression level or a newer deflate could cut the rest, but changes the save bytes, so it needs care (the game must still read them, and saves must stay compatible with the unpatched game).

## Sleep polling waits

A static pass over `witcher.exe` for 2007-era habits found the usual suspects already fine (LAA, LFH on the process heap, D3D9 device flags `0x142` without `MULTITHREADED`, effects begun with `D3DXFX_DONOTSAVESTATE`, resource files opened with `FILE_FLAG_SEQUENTIAL_SCAN`, texture loader thread blocking on semaphores). What stands out is waiting by Sleep polling:

- **Texture wait after loads:** `module.luc` `OnLoaded` calls `AurWaitForAllTexturesToLoad`, which sets `0x00CBAE38`; on the next frame `FUN_00588460` calls `FUN_006e8170`, which processes finished textures and, while the loader's pending queue (`[0x00C58C3C]+0x28/+0x2C`, 0x94-byte items) is not empty, does `Sleep(250)` (`0x006E81DB`). Each load can lose up to 250 ms per round.
- **Resource wait:** `FUN_0081a7a0` polls `FUN_007f5b40` with `Sleep(5)` (`0x0081A8A0`) when the main thread needs a resource that is being loaded asynchronously.
- **Spinlock:** `FUN_00456040` (and inlined copies around `0x009D8000-0x009D9D00`) does `Sleep(1)` while `InterlockedExchange` fails. Without a raised timer resolution `Sleep(1)` lasts ~15.6 ms (seen in the harness); DXVK may raise it in game.
- Minor: the main loop runs four console commands as text every frame (`"g_nGetGOCalls 0"` etc.); microseconds, not worth a patch.

`[debug] wait_timing=1` measures these: it swaps the exe's `Sleep` import (`0x00B3F22C`) for a hook that sums requested and actual sleep per caller (return address, main thread or other) and logs one line per burst, and it wraps the texture wait (`0x005884A2`) to log its total time, the number of `Sleep(250)` rounds and when the pending queue actually emptied. Harness-tested. In game (2026-10-19, a save load and an interior door in Vizima, in and out) the texture wait had nothing pending all three times and there were no resource-wait or spinlock sleeps at all; on a large transition the texture wait slept 242 ms on an empty queue (see Area loading), which fix 9 removes.

## Area loading

3-5 s stretches on the main thread inside `d3dx9_35.dll` with no game frame on the stack. With Microsoft's public PDB (`d3dx9_35.pdb`, GUID `8E77222E6AC24E33A4FF54C7F6A052D7` age 1, resolved with `cdb -z C:\Windows\SysWOW64\d3dx9_35.dll`) the two long loads in the Vizima profile (0-3 s and 134-139 s, 790 samples) are 99% inside `D3DXCreateTextureFromFileInMemoryEx`, almost all of it `D3DXFilterTexture` → `CBlt::BltBox2D` with DXT codecs: `D3DXEncodeBC5S` 41% (probably folded with the DXT5 alpha-block encoder), `CCodecDXT::Decode` 16%, `D3DXDecodeDXT1` 12%, `D3DXEncodeDXT5` 10%, `D3DXDecodeDXT5` 5%. So the load time is **mipmaps built on the CPU**: each level is decoded from DXT, box-filtered and re-encoded.

The call (`0x0053FAC3` in `FUN_0053f910`) passes the resource's DDS (header in front of the data) with Width/Height `D3DX_DEFAULT`, MipLevels `D3DX_DEFAULT` (full chain), Format `D3DFMT_FROM_FILE`, MANAGED, Filter/MipFilter `D3DX_DEFAULT`.

Measured in game with `[debug] texture_timing` (2026-10-19, Temple Quarter ↔ Trade Quarter): one transition creates ~900-1150 textures in 1.0-2.8 s; 300-450 of them are DXT DDS files with **no mips in the file** (`header mips 0`), whose levels D3DX builds in ~1-1.5 s. They are mostly UI and fog of war (`ui_background_01..03`, `ui_main_mask`, `ui_main_back` at 2048x1024 DXT5 ~70 ms each, `fogofwar`/`foggl19`/`gui_replace01` at 1024x1024 ~35-43 ms), and the GUI ones are recreated on every load. Textures with all levels in the file cost ~1 ms each (D3DX copying, plus RGB24 → X8R8G8B8 expansion for some). **Fix 8** caches the built levels on disk ([fix8-mip-cache.md](fixes/fix8-mip-cache.md)).

The texture wait does sleep on large transitions: the old Vizima profile shows it (`wait<-witcher.exe+2e81e2`, 58 samples at 128 s), and `wait_timing` on Trade Quarter ← Temple Quarter logged 8 textures pending, the queue empty after 9.5 ms and 242 ms slept on an empty queue. **Fix 9** polls with `Sleep(1)` instead.

## Lag after alt-tab

2026-10-19: after alt-tabbing back into the game it stayed laggy ("like a low frame rate") until the next alt-tab out and in. Not the main loop's background sleep: the main loop sleeps 1 s per frame when the window is minimized, or when it is fullscreen (`[0x00EE47BC]->vfunc+4`, the same flag that selects `Windowed = 0` at device creation) and `GetWindowInfo` lacks `WS_ACTIVECAPTION` (`0x007532C2`-`0x0075330E`, flag `0x00C2A324`), but `wait_timing` showed no such sleeps during the laggy stretch, only before (while the owner was in another window) and at the second alt-tab. So the frames were slow for another reason (presentation after the focus change, DXVK, the driver). `[debug] frame_log=1` logs every stretch of 3+ s below 30 FPS with how much of it the game was in the foreground, had an active caption and treated itself as inactive.

What the logs show (`frame_log`, `texture_timing`, `wait_timing`, DXVK's `witcher_d3d9.log`; 23 focus losses on 2026-10-19, 2 of them laggy):

- **Signature:** a steady ~24 FPS (23.9 and 24.3; with `d3d9.maxFrameRate = 72` that is 72/3) with the game in the foreground and active, and every D3D call slow: `CreateTexture` of a 32x32 RGB32 texture with all levels in the file takes 33-36 ms instead of 0.1 ms. So the main thread waits inside DXVK (presentation or DXVK's CS thread), not in game code. The second alt-tab cures it (the next 32x32 textures take 0.1 ms again).
- **Not the time spent outside:** the laggy ones were 6 s (18:37) and 60 s (21:43) away; 281 s, 336 s and 980 s away were fine.
- **Not simply "alt-tab during a load":** both laggy ones left the game during or right after a large area transition (900 / 640 textures created just before), but so did three fine ones (18:38, 18:49, 18:54). So far the trigger looks random.
- **What happens at each alt-tab:** the game is fullscreen (`Windowed = false`, 3840x2160) and DXVK runs it with `VK_PRESENT_MODE_IMMEDIATE_KHR`, 3 images. DXVK does no `ResetSwapChain` on focus changes; it recreates the Vulkan swapchain at 237x39 (the minimized window) when leaving and at 3840x2160 when coming back. The game recreates its ~200 GUI textures on every return (fine and laggy alike).
- Hypotheses, none verified:
  1. **Timer resolution not restored.** Windows 11 stops honouring a process's timer resolution request while its window is minimized or hidden. DXVK asks for 0.5 ms (`Setting timer interval to 500 us`); if the game kept the default 15.6 ms after coming back, every timed wait in DXVK (frame limiter, waits for its CS thread) would round up to 15.6 ms ticks, which fits "everything slow by a few ticks" (34 ms ≈ 2 ticks per texture). In the harness a process without its own request got Sleep(1) = 15.7 ms while the system timer stood at 1.00 ms (another process had asked for it), and 1.9 ms after `timeBeginPeriod(1)`. If this is it, a fix is `SetProcessInformation(ProcessPowerThrottling)` with `PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` (requests stay honoured whatever the window state), or asking for the resolution again on every return.
  2. **Presentation path.** After the swapchain is recreated the frames are composed by DWM instead of flipped, or G-Sync does not re-engage, and the next recreation puts it right. The owner finds the lag clearly worse than missing G-Sync.
- **Diagnostics since 2026-10-20 (`frame_log`):** `frames:` lines also show time in `Present` (vtable hook on the game's device `[0x00C587BC]`, slots 16/17), a frame-time histogram and how long `Sleep(1)` lasts in the game (a probe thread, 10 per second). A `focus back after N s away, first 10 s:` line after every return, followed by the window, monitor, display mode, system timer, priority and the visible windows above the game, lets fine and laggy returns be compared. `Reset` calls are logged. On the lag signature (4 s in a row at 10-30 FPS, foreground and active, no frame over 250 ms) the DLL logs the same state and, with `[debug] frame_sampler=<path to sampler.exe>`, profiles for 15 s into `System\enginefix_lag_<time>_main<tid>.csv` (at most once per 5 min). Harness-tested with a real D3D9 device: hooks, lines, signature and sampler start all work. Read the result: hypothesis 1 if `Sleep(1)` is ~15.6 ms while laggy and ~1 ms in fine returns; hypothesis 2 if `Sleep(1)` is normal and the time is in `Present`.

2026-10-24 22:38, first capture with the sampler (124 focus returns since `frame_log` went in had produced no `lag signature`): out at 22:37:39, back at 22:38:21 after 40.2 s. First 10 s 29.3 FPS, then steady 24.5 FPS with every frame 30-50 ms (40.8 ms): `Present` 31.7-33.5 ms and the main thread's own work 9.1-11.6 ms, `Sleep(1)` 1.5 ms (system timer 0.50 ms), foreground and active 100%, no visible window above it. The old texture signature came with it: a 32x32 RGB32 texture with all levels in the file took 31.5-33.8 ms again (normally 0.1 ms).

The 15 s profile (`System\enginefix_lag_223827_main42144.csv`, 2 ms interval, 13972 samples) rules out hypothesis 1 (timer resolution) for this occurrence, and the GPU, and names the waiter:

- The main thread is in **one** condition-variable wait per frame (~30 ms), reached from our own Present hook: `ntdll NtWaitForAlertByThreadId <- kernelbase SleepConditionVariableSRW <- d3d9+0x11f50f <- d3d9+0x3aeb6 <- d3d9+0x3f7b8 <- d3d9+0x3524a <- dinput8.dll+0x5d8f`. That is DXVK's `D3D9SwapChainEx::Present` → `PresentImage` → `SyncFrameLatency`/`acquireNextImage`: waiting for the frame-latency signal that DXVK's "dxvk-frame" thread emits after `FpsLimiter::delay()`, not for game code, file I/O or a timer. `tools\profiler\stacks.py` prints these chains.
- Nothing is GPU-bound: in all 13972 samples no thread waits in `vkWaitForFences`, and DXVK's CS/worker threads sit idle in their condition variables (`d3d9+0xc2d95`, `0x121cc3`, ...). EIP modules: 88.8% ntdll (waiting), 5.3% witcher.exe, 0.1% nvoglv32. So neither CPU nor GPU is the bottleneck; the frame is paced by presentation.
- The ~8% of main-thread samples that do reach nvoglv32 are the texture upload path (`FUN_006e6fa0` → `d3d9+0x104681` → ... → `nvoglv32+0x51c277`), with one 682 ms stall: the same "every D3D call waits behind the present" effect, not a separate cause.
- 24.5 FPS is exactly a third: 72/3 = 24, and the display mode is 75 Hz (75/3 = 25). DXVK's log does exist for this session (`System\witcher_d3d9.log`, v2.7.1): fullscreen 3840x2160, `VK_PRESENT_MODE_IMMEDIATE_KHR` with dynamic modes, 3 images, swapchain recreated at 237x39 on every minimise and 3840x2160 on every return, no device reset, no `Presenter: Got ...` errors, nothing at the moment of the lag.

So the presentation pipeline retires one frame per three display periods after this return while the game itself is healthy. Remaining hypotheses, both about the swapchain/display coupling, neither verified:

1. **G-Sync/WSI loop:** frame latency is 1 (`GetActualFrameLatency` = min(game, cap, BackBufferCount+1) = 1), so the app waits for the previous frame's signal every frame; an app and a variable-refresh display can then settle at a self-consistent low rate (24 Hz is also the panel's low-framerate-compensation floor). The next alt-tab recreates the swapchain and breaks the loop, which is why the second alt-tab cures it.
2. **DWM composition:** after the recreation the window is composed instead of flipped, and the frame signal then follows the composition.

Next experiments, cheapest first: `dxvk.hud = fps,frametimes,gpuload,memory` for one session (is the GPU idle during a recurrence?); `d3d9.maxFrameLatency = 2` (the maximum with 1 back buffer, decouples the app from the display by one frame); `d3d9.maxFrameRate = 0` (no limiter); G-Sync off for the game (NVIDIA profile, Monitor Technology = Fixed refresh). And start the sampler on the focus-back instead of 6 s later: the steady state is known now, the transition is not (the sampler run began 6 s after the return, and the 682 ms texture stall is the only trace of it).

The borderless window (QoL 3, 0.5.0) avoids the exclusive-mode path altogether: DXVK keeps one swapchain, and the game recreates only a few GUI textures on a return (3-30 instead of ~200). If the lag shows up again, note which mode the game was in.

The "stall in heavy combat in the swamp" (2026-10-18: ~54 s of main-thread waits in DXVK, `d3d9.dll+0x11f50f` `SleepConditionVariableSRW`, slow `CreateTexture` calls at `0x53F02A` and `0x6E7045`, smooth again after a reload) has the same signature, and the owner tied it to an alt-tab once the alt-tab lag was known. It was first taken for DXVK shader compilation in combat; that was never confirmed, so treat it as this issue. Note: OBS's implicit Vulkan layer injects `graphics-hook32.dll` into DXVK games even when OBS is not running.

## Above 60 FPS

PCGamingWiki says high FPS causes "hair physics glitch and crashes at anytime, in addition to script issues" and recommends a 60 FPS cap. The crash and script claims trace back to an old 120 Hz report that we could not read; the hair reports (Abigail, the Reverend, Geralt; fixed by vsync or a ~58-60 cap) are consistent. Here the cap is DXVK's `d3d9.maxFrameRate = 60`. What the engine does with frame time (static analysis, not tested in game):

- **Timer:** 64-bit microsecond counter (`FUN_007fda90`/`FUN_007fdaf0`, RDTSC calibrated against QPC), so frame time is precise at any FPS. `g_cAuroraSettings.m_bStaticTimeFlow`/`m_nStaticTimeFlowFPS` (`0xC500E8`/`0xC500EC`) is a built-in fixed-time-per-frame mode (for cutscene recording), not a fix.
- **Rigid-body physics (Karma-style world):** frame-rate independent. `FUN_008377e0` adds dt (µs → s) to an accumulator and runs fixed steps of `1/m_fPhysicsStepsPerSecond` (`0xC50A30`; camera world `0xC50A34`, minigames `0xC50A38`), at most 15 per frame (time beyond that is dropped), with no interpolation. Above the step rate, physics objects move only on some frames. `startup.luc` sets the rates to **30 / 30 / 90** (confirmed in the live process 2026-10-20), so loot, debris and objects pushed by Aard move at 30 Hz at any frame rate: speed and paths are the same at any FPS, only the smoothness differs. At 60 FPS every step shows for exactly 2 frames (even); at 72 FPS for 2 or 3 frames in turn (slightly uneven), and the same at any FPS that is not a multiple of 30. No interpolation found: in the physics code (`0x828000`-`0x840000`) only the init `FUN_00837c60` (`1/rate`) divides by the step; the accumulator remainder (`world+0x58`) is never used for rendering. Possible but untested remedies: raise `m_fPhysicsStepsPerSecond` (the Karma-style solver is tuned at 30 Hz, so contacts, damping and CPU cost may change; check stacking and resting objects) or add interpolation (large). Not worth it unless the owner sees judder.
- **Cloth (`MdlNodeCloth`, `m_bEnableClothySimulations`):** frame-rate independent. `FUN_005645d0` substeps at 100 Hz (dt clamped to 0.3 s), `FUN_00565980` at 200 Hz (dt clamped to 0.05 s). Above 100 FPS the 100 Hz cloth gets 0 steps on some frames (judder, not wrong motion).
- **Dangly nodes (`MdlNodeDanglyNode`, hair):** **frame-rate dependent damping.** The update `0x552B70` integrates force and position with dt (clamped to 0.05 s), but multiplies the velocity by the damping once per frame. An earlier note here said dt was never read; that was a misread of the stack offsets. **Fixed by fix 6** ([fix6-dangly-damping.md](fixes/fix6-dangly-damping.md)); still to be tested in game.
- **Game time (day/night, calendar):** frame-rate independent. The world timer `FUN_007556c0` adds the difference between absolute engine-clock readings (`FUN_007f60c0`, µs, 64-bit) each frame, so nothing is lost to rounding at any FPS. A time multiplier (`[timer+0x48]`, for slow motion) goes through a float conversion, at most ~1 µs per frame. Hours and minutes are derived from it (`FUN_00755880`: minutes-per-hour × 60000 ms).
- **Per-frame budgets:** `m_nPathFindingTimeSlicePerFrame`, `m_nPathFindingMaximumTimePerFrame`, `m_nPendingDecalsPerFrame`, `m_nNumTexturesToDownsamplePerFrame`. Higher FPS only means more of this work per second, not wrong behaviour.
- **Not yet checked:** camera smoothing, UI/Lua animations, NWScript timing. Combat timing is not traced in detail, but it is driven by the world timer and animation time (both time-based) and no per-frame counter turned up. Find these by playing with the cap raised (72 FPS on the owner's 75 Hz G-Sync screen).

Once fix 6 is tested in game, check whether the hair glitch reports are fully explained by the damping or whether more remains (e.g. jitter at very high FPS).

## Draw distances

`[graphics] detail` ([graphics-detail.md](fixes/graphics-detail.md)) multiplies the LOD, grass, shadow and light distances in `g_cAuroraSettings`; the factors are a first guess until measured in game (Ctrl+F12 with `detail_hotkey`, frame rate and main-thread time per level in the log). The water reflection texture (`m_nReflectionRTSize`, 512 px) is in it since 2026-10-20 (1024 / 2048), not tested in game yet. Not included yet, each needs a look first: `m_fGrassDensityModifier` (set by the grass slider, 1.0 at most), `m_fCharacterVisibility` (per location from a 2DA, `FUN_0040b420`, on every area load) and `m_fPlaceableVisibility` (120 from `startup.luc`).

## Stuck after a conversation (can walk, cannot act)

Seen once (2026-10-20, Lakeside, chapter 4): after talking to a sleeping NPC, Geralt could walk but not attack, interact or use Space. The log shows two loads before quitting, so loading apparently did not help; after a restart the newest save was fine. So the state lives only in memory and is not saved. No log covers it; next time, take a full dump of the running game before loading or quitting.

What the code shows so far (Ghidra, not verified in game):
- `FUN_008a15e0` is `AIActionDialogObject` (the action that starts a conversation). It has about 15 abort paths ("***Dialog interrupted due to ...": speaker dead, combat mode, despawn, knockdown/sleep effect on the target, NPC already in a non-interruptable dialog, dialog file failed to load, ...). They go to the engine's log function `FUN_00546030`, which writes nowhere in retail. `[debug] engine_log` (2026-10-20, on in the owner's ini) copies them into our log as `engine: ...` lines, so the next occurrence shows which path ran.
- For the player it first calls `FUN_008b7350(2)`, `FUN_008b18f0(8,0)` and `FUN_008b18f0(1,0)` (state bits at `creature+0x350` `+0x1e0`/`+0x1e4`; bit 8 = taking part in a dialog, set per speaker in `FUN_00868e00`, cleared in `FUN_00868ca0`), and the "Cannot load dialog" paths return without restoring them.
- Engine bug: `FUN_008aaf80` is meant to clear the active bits 2, 8, 0x1000 and 0x40000 before a mode switch, but tests `(flags & bit) == 1`, which is only ever true for bit 1. So a mode switch never ends an active dialog bit. Whether that bit blocks player input is not established: `+0x1e0`/`+0x1e4` are read in ~180 places across several structs. `engine_log` also logs every change of the dialog bit (`FUN_008b18f0`) and every time `FUN_008aaf80` leaves one of these bits set. Not fixed on purpose: `FUN_008b7350` (21 callers) relies on it, and fixing it would end dialogs on mode switches the game was tested without. Fix it only if the log ties it to the stuck state.

## Combat lock (both sides idle, attacks refused)

Seen 2026-10-25 21:24 (chapter 5, Vizima, the Order against the Scoia'tael), and earlier in chapter 5 with charge attacks unlocked: Geralt and an enemy stand in combat idle, neither attacks, holding the mouse button does not even start a charge; moving away ends it. Caught live: engine combat dumps switched on in the running game, two full dumps (`witcher-crash-lab\logs\dumps\manual\witcher.exe_261025_213459.dmp`, `_214100.dmp`).

- **Correction (second occurrence, 22:01-22:02, same battle):** the player's failed clicks are `CMessagePlayer_Input_AttackFailed on server` (12 in 21 s). That is the server handling message 0x28 (case `'('` in `FUN_0096fb70`, `0x97014C`), which the **client** sends when it has decided the attack cannot be made; the owner saw the crossed-out sword cursor (`MOUSECURSOR_NOATTACK` = 9; the GUI's current combat cursor is `CGuiInGame+0x120`) while the enemy kept hitting him. The three `m_bActionBlocked` lines of that session got no `combat log: attack REFUSED` line, so they were NPCs' attacks (the hook only reports the player; the harness covers that path). So the `m_bActionBlocked` line in the first lock was most likely an NPC's too, and the player's attacks fail client-side in both. Common to both: a big Order-against-Scoia'tael fight where the enemy is also fighting Order soldiers (`Scoia is breaking sequence of Order` right before the failures; in the first dump the Scoia'tael's round targets were two Order soldiers). Next: find the client-side check that picks cursor 9 and sends 0x28, and log its reason.
- **Third and fourth occurrence (22:07, 22:13):** the attacks reach the server, the charge ends in `Powerup failed` and each attack is cancelled at once (`Wiedzmin: Attack cancellation requested` → `calling ECR from sequence End()`), with `PARRY - terminating sequence` around it. In a dump during the third, Geralt was the only one of 60 creatures "in a sequence" (`+0xC58` = 1, sequence 0x26E `Steel Sword Fast 03`) without an active combat round; the one NPC in a sequence had a round. His enemy was the target of three Order soldiers and in a fourth's sequence. The AI has per-creature locals for how many may attack one target (`n_mod_max_attackers`, `n_attackers_amount`, `n_mod_pc_attacker`, `n_mod_lock_attacks`, `b_disable_attack`; name table at `0xBD7988`), their use is not traced. The crossed-out cursor of the second occurrence is chosen in `FUN_0041d0f0` (cursor 9) when the hovered creature's stats `+0x2C4` is set, which is the `Plot` flag (GFF field `Plot`, `0x008D205D`; NWScript `SetPlotFlag`), or when a player mode (`FUN_004034c0`) is 2. `combat_log` now also logs who ends the player's sequence (`FUN_008a45f0`) and who cancels his attack (`FUN_008b47d0`), with the code addresses on the stack, and when he stays in a sequence without a combat round for 1.5 s.
- **Cause found (fifth occurrence, 22:18, with the extended combat_log):** a charge attack released while the target is out of reach cancels the attack but never ends Geralt's sequence; with no combat round he then stays "in a sequence" and every attack fails until he moves. Fixed by [fix 15](fixes/fix15-charge-out-of-reach.md). Whether locks 1 and 2 came the same way is not known (no sequence logging then); combat_log's `player STUCK` line will show any other path.
- **How a charge resolves (`FUN_008dd9f0`, node `+0x48` = phase):** phase 0 while held for less than `m_nAttackPowerupHoldDelayMs` (300 ms), then phase 1 with the load animation (anim 151, `vfunc+0x98(0x97)`), phase 2 once 300 ms plus that animation's length have passed (anim 152, `vfunc+0x98(0x98)`, the charged pose). Release in phase 2: powered attack (`FUN_008c9a40` with the powered flag 1, after `FUN_008a7c60(0, 1)`). Release in phase 0 or 1: `Powerup failed`, then a normal attack (flag 0) if the target is in reach, else the attack is cancelled with nothing shown (the fix 15 branch). No partial charge: the hold time is only used for the phase thresholds. Session 22:31-22:32: of 14 charges, the 2 that reached anim 152 became powered attacks, 6 released early became normal swings, 5 released early did nothing, 1 was cancelled by a hit (`Cancelling powerup, hit`). The load animation often started ~1 s after the press.
- **Full charges that did nothing (22:32 and 22:38): not enough Endurance.** After the release the powered attack starts (`Player Atk Anim [1 -> 9]`), then `FUN_0085ece0` (called from `FUN_00864680` and `FUN_00861880`) builds the modifiers with `FUN_008d10c0` and subtracts `block+0x4DC * block+0x4E0` (the attack's Endurance cost; the charge sequences carry 25 x 1.0, so 25 of 100) from the current Endurance (stats `vfunc+0x2C`, `GetCurrentEndurancePoints`; stored at stats `+0x1AC` by `FUN_0077b470`). If the result is below 0 (or the creature is no longer in a sequence) it ends the sequence (`FUN_008a45f0(0)` at `0x85EDD6`, the logged `player's sequence ends (0) from 85EDDB` with the player still in a sequence), and the attack is gone with nothing shown; otherwise it takes the cost and runs the attack (`FUN_0085e380`). 6 of the 9 full charges logged on 2026-10-25 ended this way. The GUI has an Endurance bar red blink (`TriggerEnduranceRedBlinkBlink`, called from `FUN_00466fe0`); [QoL 8](fixes/qol8-endurance-blink.md) now triggers it in this case.
- What follows was written before that correction. The `m_bActionBlocked` check is at `0x864BC2` in `FUN_00864ae0`: `FUN_008d10c0` (thiscall, ret 0xC; owner `[creature+0xADC]`, target) builds the attacker's modifiers against the target in the static block `0x011BF018` (0x618 bytes), and `+0x5F4` set means blocked. The block starts from `0x011BEA00` and adds, with `FUN_007a02f0` (flags at `+0x5F4`.. are ORed), the abilities of the equipped items, the creature's abilities (stats `+0x398`, indices into the table at `[0xC51BAC]`, block at ability `+0x5C`), its effects (stats `+0x3AC`, 0x30-byte entries, `FUN_0077e300`, block at `+0x90` or `+0x6A8`), an extra ability list, and the attack sequences of both sides (table `[0xC559DC]`, 0xE9C bytes per sequence, attacker block `+0xEC`, target block `+0x704`).
- In both dumps no ability (989), no sequence (1423, either block) and not the base set `+0x5F4`, and Geralt had no effects. So the flag came from something short-lived, or from a path not yet seen.
- Geralt's state in the lock: empty action queue, still in an attack sequence (`+0xC58` = 1, sequence 0x26E) with no active combat round (round `+0x1D8` = 0), `+0x94C` = 0x1DF9, a creature that had been freed by the second dump. Around him a Scoia'tael (0x1EFD) looped `Server stance [BeforAtk]` → `Attack cancellation requested` → `calling ECR from sequence End()` without ever striking.
- The engine's combat dumps are `g_cAuroraSettings` flags: `m_bDumpPlayerCombatRounds` (`0xC50250`), `m_bDumpPlayerAttackData` (`0xC5024C`), `m_bDumpAttackCancellationInfo` (`0xC5023C`), `m_bDumpCombatInformation` (`0xC50340`). `m_bDumpPlayerInterruptableActions` (`0xC5034C`) and `m_bDumpStances` (`0xC50264`) write hundreds of lines a second and push the others out. The charge attack is action 0x45, `aiactionattackpowerupload` (`FUN_008dd9f0`, hold delay `m_nAttackPowerupHoldDelayMs` = 300 ms); a hit during it logs `Cancelling powerup, hit` (`FUN_008c2070`).
- **`[debug] combat_log`** (2026-10-25, on in the owner's ini) turns those four dumps on (and engine_log with them) and, for every refused attack of the player, logs the summed blocks that carried the flag, named (ability with its name, sequence and which block, or the start of the unknown object) with the call site in `FUN_008d10c0` they came from, plus the player's sequence, round and targets. "no summed block carried the flag" would mean the flag is written some other way. Next lock: read those lines, then decide the fix (end the stale sequence, or drop whatever left the flag).

## Snipping Tool does not open over the game

Win+Shift+S and Print Screen (with "Use the Print screen key to open screen capture") do nothing while the game is in front, in full screen and borderless alike. The game's DirectInput keyboard (`FUN_004cc720`, `GUID_SysKeyboard`) is set up with `SetCooperativeLevel(top window, 0x16)` = `DISCL_NONEXCLUSIVE | DISCL_FOREGROUND | DISCL_NOWINKEY`. A test window (2026-10-22) with the same setup blocked both hotkeys; with `0x06` both opened the Snipping Tool. The exclusive DirectInput mouse (`FUN_004cc670`, `DISCL_EXCLUSIVE | DISCL_FOREGROUND`, acquired whenever the game has the focus) blocked neither. Dropping `DISCL_NOWINKEY` (`push 0x16` at `0x004CC7C4`) would also let a lone Windows key open the Start menu in game. Done as [QoL 6](fixes/qol6-windows-key.md): `0x06`, and a thread that presses the unassigned key `0xE8` as soon as the Windows key goes down in game. A low-level keyboard hook in the game's process saw no keys at all while a DirectInput keyboard was acquired (not even with a fresh hook installed after DirectInput's), so it watches `GetAsyncKeyState` instead.

## Other observations

- At the 60 FPS cap the main thread is busy 40-50% of the time in Vizima and the swamp; the game is not CPU-bound in normal play.
- The engine is effectively single-threaded (main thread: logic, AI, all D3D calls). DXVK already moves submission to its own thread.
- `.bfx` files in `System\Scripts` are precompiled effects; `FUN_00525ae0` only compiles `.fx` when a newer source exists (flags `DAT_00c50148`/`DAT_00c50150`, both 0 in retail).
